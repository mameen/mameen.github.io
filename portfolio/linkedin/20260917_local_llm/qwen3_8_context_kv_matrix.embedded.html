Where Qwen 3.8 27B stops being a fast 24 GB GPU model.

One model. Six requested context sizes. Two KV-cache representations. The question was not “can it start?” but “when does it stop behaving interactively?”

12 fresh runs · prompt: “Write a 1000 words story then stop.”
Read this first

VRAM residency, not model quality, is the limiting resource.

The official Qwen checkpoint is unchanged in every experiment. What changes is the memory needed beside the model: the KV cache is allocated for the requested context. During decode, the runner repeatedly accesses its weights and active cache for every new token. Once the runner no longer remains fully in the RTX 4090's 24 GB VRAM, host-memory offload enters the path and decode throughput falls sharply.

Context size

The context window is the maximum number of tokens the model can keep available for one request. Bigger windows need more working memory, even when the actual prompt is short.

KV cache

The key-value cache is the model's short-term working memory. It stores compact representations of earlier tokens so each new token can use the conversation so far without recalculating everything.

Quantization

Quantization stores numbers with fewer bits. Here, q8_0 compresses the KV cache - not the Qwen model weights - to use less VRAM. This report measures speed and memory, not answer quality.

The first-order cache math

Qwen 3.8 uses 16 gated-attention layers, with 4 KV heads of 256 values each.

K + V cache
16 layers × 4 KV heads × 256 values × 2
= 32,768 values / token

f16 cache
32,768 × 2 bytes = 64 KiB / token
256K × 64 KiB = ~16 GiB raw KV data

q8_0 makes raw KV values roughly half that size
before metadata and runtime overhead.

What this experiment directly measures

This is a focused allocation, residency, and decode-throughput study. Each run reserves the requested num_ctx capacity, then generates a requested 1,000-word story with a 2,048-token ceiling. That makes the runner-memory readings and TPS values directly relevant to sustained local generation on this Ollama setup.

Its 21-token input intentionally avoids mixing long-prompt ingestion with decode. A separate filled-context prefill test would answer a different question; it does not weaken this result.

Why q8_0 won the token test

q8_0 quantizes the KV cache, not the Qwen model weights. That reduces cache memory pressure while preserving the same official checkpoint.

At 64K, that is the decisive distinction: f16 has already offloaded 1.28 GB, while q8_0 remains fully resident. The observed result is 45.61 TPS versus 83.00 TPS.

The answer

Not all context is usable context.

q8_0 buys headroom by shrinking the KV cache. It delays the VRAM cliff; it does not eliminate it.

Method

What changed and what did not

Held constant

Official Qwen 3.8 27B Ollama tag, CUDA, Flash Attention, the literal prompt Write a 1000 words story then stop., and one fresh runner for every point.

Changed on purpose

Requested context size and only the KV-cache representation: f16 versus q8_0. Model weights were not replaced or re-quantized.

Measurement scope: the TPS chart measures decode speed after generation begins. The readiness chart is a cold server counter, not observed streaming TTFT. A warm streaming TTFT test and a multi-user concurrency test are separate application measurements.

Evidence: 12 successful fresh runs. Context sizes: 8K, 16K, 32K, 64K, 128K, 256K. Some stories naturally ended before the 2,048-token ceiling; each TPS value uses the actual generated-token count returned by Ollama.
